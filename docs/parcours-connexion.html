TP1 — Angular ↔ Express ↔ MongoDB

Parcours de connexion

Ce que déclenche un clic sur « Se connecter » dans login-page.html, jusqu'à l'arrivée sur /tracks — et pourquoi certaines routes de l'API n'exigent jamais ce jeton pendant que d'autres le réclament à chaque appel.

1. Le clic, étape par étape

Cinq acteurs réels du code, dans l'ordre où ils se parlent. Le trait plein vert suit le chemin réussi ; le trait pointillé rouge, le rejet à 401 — les deux repartent du même point, la vérification du mot de passe.

2. Contrat API — routes publiques vs protégées

Directement depuis API_CONTRACT.md : la ligne d'en-tête du contrat dit tout — « Sauf inscription et connexion, envoyer Authorization: Bearer <token> ». Une route protégée passe par le middleware auth de app.js, qui rejette toute requête sans jeton valide en 401 avant même d'atteindre MongoDB.

Méthode Route Accès Requête Réponse
GET /health Publique — {"status":"ok"}
POST /auth/register Publique {name, email, password} 201 {token, user}
POST /auth/login Publique {email, password} 200 {token, user}
GET /users/me Protégée JWT 200 User
PUT /users/me Protégée {name} + JWT 200 User
GET /tracks?page&limit Protégée JWT Page<Track>
POST /tracks Protégée multipart: audio, title + JWT 201 Track
GET /tracks/:id/audio Protégée JWT flux audio
DELETE /tracks/:id Protégée JWT 204 (bonus)
